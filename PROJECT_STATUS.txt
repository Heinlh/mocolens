3. BACKEND - STRUCTURED TRANSFORM LAYER (Python, src/mocolens/processing/transforms/, storage/)
--------------------------------------------------
Status: DONE and verified against the real 351,912-record download, with
every number cross-checked against manual counts of the raw data.

Turns raw Socrata JSON into curated fact_crashes / fact_participants
tables (§10, §11, §26). All normalization is SQL run through DuckDB
itself (CREATE MACRO for the messy enum values, CREATE TABLE AS SELECT
for the transform) - no pandas/polars dependency, and every step is a
query you can run by hand to debug.

Files:
  src/mocolens/processing/quality.py            - QualityReport / run_check:
                                                    "hard" checks raise,
                                                    "soft" checks are logged
  src/mocolens/processing/transforms/vision_zero.py - the actual normalization
  src/mocolens/storage/duckdb_store.py           - connect/export_parquet/
                                                    dim_date view
  src/mocolens/processing/curate.py              - orchestrator, finds the
                                                    latest raw snapshot,
                                                    writes logs/curation/runs.jsonl
  scripts/build_curated_tables.py                - CLI: python scripts/build_curated_tables.py --domain vision_zero

Real-data quirks this was built to handle (found by inspecting the actual
downloaded Socrata data, not assumed - see the file's module docstring):
  - injury_severity / acrs_report_type / collision_type mix ALL-CAPS and
    Title Case for the same value ("NO APPARENT INJURY" vs "No Apparent
    Injury") - canonicalized via SQL macros.
  - crash_incidents had one real exact-duplicate report_number - deduped
    via ROW_NUMBER, counted as a quality violation, not silently kept.
  - the real Socrata schema has no participant age or municipality field
    at all, despite the architecture doc's suggested §11 model listing
    them - not fabricated. dim_location was skipped entirely for the same
    reason (nothing to populate it with yet); dim_date is a VIEW computed
    from fact_crashes.crash_date, not a materialized table, so it can
    never drift out of sync.
  - out-of-bounds coordinates, missing injury_severity, and orphaned
    participant rows (a driver/non-motorist row whose crash_id has no
    matching incident) are all real in the data - nulled/flagged and
    counted, never silently dropped or crashed on.
  - an empty raw JSON snapshot (`[]`) makes DuckDB's schema inference
    collapse to one untyped column - caught explicitly with a clear
    error instead of the cryptic BinderException it produces otherwise.

Quality checks, run live against the real data: 10 checks (3 hard, 7
soft). All 3 hard checks passed. Soft checks surfaced real findings:
1 duplicate crash row, 2 orphaned participants, 3,478 missing injury
severities, 91 out-of-bounds coordinates, and - the most interesting one -
31 crashes police classified as "Fatal Crash" with no participant record
marked fatal (a cross-check between two independent severity signals in
the source data, not a bug in this pipeline).

Verified live, every number cross-checked against a manual pass over the
raw JSON: fact_crashes = 124,769 rows (124,770 raw - 1 duplicate, exact
match); severity breakdown property_damage/injury/fatal = 82,463/41,904/
402 (fatal count unchanged by dedup, exact match); fact_participants =
227,142 rows (219,644 drivers + 7,498 non-motorists, exact match);
participant_type breakdown pedestrian/cyclist/other sums to exactly 7,498.
Reran the full pipeline twice (idempotent - CREATE OR REPLACE, no
duplication). Parquet exports independently re-read via a fresh
read_parquet() call, not just checked for existing. dim_date view and a
real analytical join (pedestrian crashes per year) both work.

Tests: tests/processing/test_quality.py (the run_check primitive: pass/
fail/hard-raise/threshold) and tests/processing/test_transforms_vision_zero.py
(19 tests against a synthetic snapshot deliberately seeded with every
real-data quirk above - case variants, the duplicate, null injury
severity, out-of-bounds coords, an orphaned participant, an unparseable
date, an unrecognized severity string, and the empty-array edge case).
All 21 passing. Found and fixed two real bugs while writing these: DuckDB
can't bind a prepared parameter inside CREATE VIEW (path is escaped and
inlined instead), and a CTE referenced by a later quality-check query
needed to be a materialized table instead (scope issue, not a logic bug).

4. RETRIEVAL TOOLS (Python, src/mocolens/retrieval/)
--------------------------------------------------
Status: DONE. All 5 tools from architecture doc §14 built and tested (91

Files:
  src/mocolens/retrieval/sql_tool.py           - query_analytics (§14.1)
  src/mocolens/retrieval/report_tool.py        - search_reports (§14.2)
  src/mocolens/retrieval/metadata_tool.py      - get_source_metadata (§14.3)
  src/mocolens/retrieval/statistics_tool.py    - calculate_statistics (§14.4)
  src/mocolens/retrieval/visualization_tool.py - build_visualization_spec (§14.5)

query_analytics is the one worth real attention - it runs SQL an LLM will
eventually write. Every layer below was verified empirically against a
running DuckDB instance, not assumed safe from documentation:
  1. The query never touches the real analytics.duckdb file. A fresh
     in-memory connection loads ONLY the allow-listed tables straight
     from their Parquet exports - no ATTACH at all. Confirmed empirically
     that ATTACH ... READ_ONLY + exposing one view is NOT sufficient on
     its own: a schema-qualified name (src.other_table) still reaches
     every table in the attached database regardless of which views
     exist. This would have shipped as a real hole if not tested.
  2. `SET enable_external_access = false` after loading the trusted
     tables - disables read_parquet/read_csv/COPY/ATTACH from inside the
     query text entirely, and DuckDB refuses to let a later statement
     turn it back on. Without this, a crafted query could read (or COPY
     out) any file on disk the process can see, regardless of which
     tables were "loaded" - also confirmed empirically, also would have
     shipped as a real hole.
  3. Query text is parsed with DuckDB's own parser (extract_statements),
     not regex - exactly one statement, type must be SELECT. A textual
     backstop additionally rejects pragma/attach/copy/etc. as whole
     words, because at least one informational PRAGMA parses as
     StatementType.SELECT - confirmed empirically. (An earlier version of
     this backstop used substring matching and would have rejected any
     legitimate query using SQL's OFFSET clause, because "offset"
     contains "set" - caught by testing, fixed with word-boundary regex.)
  4. Always wrapped in SELECT * FROM (...) LIMIT n regardless of what the
     inner query does.
  5. A watchdog thread calls connection.interrupt() after a timeout -
     confirmed this actually aborts a running query.
  Every call is also logged to logs/retrieval/sql_queries.jsonl (question,
  sql, reason, row_count or error) for audit.

Tests: tests/retrieval/ - 91 tests across all 5 tools. sql_tool's 26
include a full adversarial battery (multi-statement, DROP/INSERT/UPDATE/
DELETE/CREATE/ALTER, ATTACH, PRAGMA, COPY, a read_csv_auto filesystem
escape attempt, an unknown-table reference, a slow-query timeout) plus
regression tests for both real bugs found while building this (the OFFSET
false-positive above, and DuckDB's CREATE VIEW not accepting a prepared
parameter). metadata_tool and report_tool each include one live test
against the real ingested data/index (skipped gracefully if that data
hasn't been built yet, so the suite still passes in a fresh checkout).

A real, non-cosmetic bug was found and fixed while wiring this up:
agency_name - the closest real "area" proxy fact_crashes has - turned out
to have the SAME messy-casing problem as injury_severity/acrs_report_type,
but worse: each of the 5 real reporting agencies appears under TWO
different raw strings (e.g. "MONTGOMERY" and "Montgomery County Police";
"Rockville Police Departme" is truncated mid-word by what looks like a
Socrata field-length limit). A naive GROUP BY agency_name was silently
splitting every real agency into two "different" hotspot areas on the
dashboard map - only caught by actually looking at the rendered
screenshot, not by any automated check. Fixed at the curation layer (a
new normalize_agency() SQL macro in transforms/vision_zero.py, the same
pattern as the other normalize_* macros) so every consumer benefits, not
just this one endpoint - plus a new soft quality check
(unrecognized_agency_name) so a future 6th agency shows up as a flagged
anomaly instead of silently passing through unmapped. 2 new regression
tests added; curated tables rebuilt and reverified.

Also fixed while building this: an early version of the dashboard's
"insights" text compared the crash-trend chart's first and last months
directly and reported "crashes have risen 320%" - which was entirely a
partial-month edge-boundary artifact of a fixed 13-month trailing window,
not a real trend (§27's "avoid false precision" territory). Fixed by
reusing the already-robust trailing-12mo-vs-prior-12mo comparison that's
computed for the "Total crashes" KPI card instead of the fragile
month-endpoint comparison.

LLM: Azure OpenAI, gpt-4.1-mini, via langchain-openai's AzureChatOpenAI.
Went through two provider changes to get here, each for a real reason,
not indecision:
  1. IBM watsonx.ai (ibm/granite-4-h-small) - the user's original choice,
     continuing the IBM stack from the processing layer. Built and
     integration-verified (schemas, field names, all confirmed against
     the installed package), but blocked on IBM Cloud account
     configuration that took most of a session to diagnose: an invalid
     API key (traced to a mis-copied value, not a code bug), then a
     watsonx.ai project with no Watson Machine Learning instance
     associated, then account-level Lite-plan quota conflicts from
     leftover auto-created WML instances. None of this was a code
     problem - every failure was confirmed as a clean, specific error
     from IBM's own services (auth rejection, then a clear
     no_associated_service_instance_error), not a crash or a guess.
  2. Azure AI Foundry with a Granite model - considered next, but
     checked Microsoft's own current (dated 2026-07-16) Foundry "Featured
     models" catalog before writing any code: IBM/Granite is not a
     first-party serverless model there. The only Granite-on-Azure path
     is self-hosted managed compute (a continuously-billed GPU VM),
     which is a bigger commitment than the watsonx account issue being
     worked through, not a simpler alternative to it.
  3. GitHub Models was considered as a free, zero-infrastructure
     alternative - checked GitHub's own current docs before recommending
     it and found it was fully retired on 2026-07-30, a month before this
     session. (Several independent "free LLM API" listicle sites still
     described it as live and current - a reminder that those aggregator
     sites lag reality and aren't a substitute for checking the primary
     source.)
  4. Landed on Azure OpenAI gpt-4.1-mini (gpt-4o-mini's replacement,
     since deprecated), funded by the user's Azure for Students credit -
     genuinely available today, tool-calling reliability is the most
     battle-tested of any option considered, and langchain-openai's
     AzureChatOpenAI integration worked correctly on the first real
     attempt once credentials were in place - no equivalent friction to
     watsonx's account-configuration maze.
Docling and the Granite embedding model (section 2) are completely
unaffected by any of this - they're separate, local, already-working
components with zero dependency on which chat LLM the agent calls. Only
the agent's LLM changed; the "IBM stack" everywhere else did not.

Credential handling: the user pasted a real Azure API key directly into

Graph shape:
    START -> agent --(tool calls requested)--> tools --(cycles left)--> agent (loop)
                  \\--(no tool calls)--> finalize              \\--(3 cycles used)--> finalize
                                                                                          |
                                                                                          v
                                                                             validate_citations -> END

validate_citations is deterministic Python, not another LLM call: it
strips any citation the model produced that doesn't correspond to an
actual search_reports/get_source_metadata result seen earlier in that
same run (matched by title or URL) - so a hallucinated source can never
reach the user, and if no report/metadata tool ever ran, every citation
is stripped regardless of what the model claims (§27, §33.10).

A real design bug was caught while writing the cycle-limit test, not
assumed correct: the first version checked the cycle cap inside the
"agent" node's routing function, which meant after the 3rd tool execution
the agent got called a 4th time to "plan again," and that 4th call's
tool-call decision was silently discarded once cycle_count already hit
the cap - a wasted LLM call on every maxed-out conversation, real cost on
a paid API for nothing. Fixed by moving the cap check to right after tool
execution (route_after_tools) instead of after the next agent call
(route_after_agent) - confirmed via a test asserting the exact LLM
invocation count, which caught the off-by-one before it could ship.

Tests: tests/agent/test_graph.py (9 tests) use a hand-written scriptable
fake chat model (implements .bind_tools()/.with_structured_output()/
.invoke() - the same interface any LangChain chat model exposes) instead
of a real API call, so these run without credentials, cost nothing, and
are deterministic. Cover: no-tools-needed short-circuit, single tool
cycle then finalize, the cycle-limit fix above (asserted via exact LLM
invocation count), finalize actually receiving tool results in its
message history (not just the original question), and 5 citation-
validation cases (a real citation kept, a hallucinated one stripped, all
citations stripped when no search ever ran, title-differs-but-url-matches
still counts as real, a non-list tool result like query_analytics'
dict output doesn't crash the matcher). tests/agent/test_llm.py (4 tests)
covers missing/partial/whitespace-only credentials and that surrounding
whitespace gets stripped before use. All 13 passing, plus the 2 real live
runs described at the top of this section - the fake-LLM tests prove the
graph's control flow is correct; the live runs are what actually prove
gpt-4.1-mini picks the right tools and produces a schema-valid, grounded
answer for a real question, which no amount of fake-LLM testing can prove
on its own.

RESOLVED ISSUES
==================================================
1. [RESOLVED 2026-08-31] Processing pipeline crash (exit code 4, no
   traceback) partway through a full run. Root cause confirmed:
   RapidOCR was reloading its detect/cls/rec ONNX models and running
   full-page OCR on every page of every PDF, even though these county
   reports are text-native and OCR always returned an empty result -
   pure wasted CPU/memory that compounded across a multi-document run
   until something got killed. Fix, two parts:
     - src/mocolens/processing/pdf_parser.py now builds the
       DocumentConverter with do_ocr=False (table-structure detection
       stays on - it's cheap and these reports have real tables).
     - src/mocolens/processing/runner.py now runs each document in its
       own subprocess (`python -m mocolens.processing.runner <domain>
       <doc_id>`), so memory is fully reclaimed between documents, one
       bad PDF can only fail itself, and a real traceback lands in
       logs/ingestion/processing_failures.jsonl instead of vanishing.
   Reran the full pipeline after the fix: all 5 documents processed,
   0 failures, 319 chunks total, confirmed searchable (see above).

2. [RESOLVED 2026-08-31] agency_name double-counting every real police
   agency into two "different" areas (raw all-caps abbreviation vs. a
   separately-truncated title-case name). See section 5's writeup - fixed
   with a normalize_agency() macro at the curation layer, a new quality
   check, 2 regression tests, and a rebuild + rescreenshot to confirm.

3. [RESOLVED 2026-08-31] A dashboard "insight" reporting a fabricated 320%
   crash increase, driven entirely by comparing two partial months at the
   edges of a fixed trailing window. See section 5 - fixed by reusing the
   already-correct trailing-12mo-vs-prior-12mo KPI figure instead.
